(Traycer mechanics, source-cited) × `docs/alloy-feature-audit.md` (what Alloy ships today,

## The one-paragraph verdict

Traycer and Alloy agree on the big architecture more than Josh's video suggests: BYOA
multi-provider seats, stored upstream CLI session ids, spawn trees as provenance, a planner
that decomposes goals into verified parallel work, human Q&A mid-run, audit trails. Where
Traycer pulls ahead is **economics and durability**: it routes every internal operation type
to the cheapest model that can do it (profiles), it makes the expensive artifact (the plan)
a first-class document handed to executors instead of relaying whole conversations, it grades
verification output so only Critical/Major findings buy another paid iteration, and its
specs/tickets/executions persist as durable intent between runs. Those four themes are where
the value is.

## Not worth copying (and why)

- **Cloud collaboration layer** — shared boards, invite-by-email, real-time co-editing,
  Editor/Viewer ACLs, organizations/billing (research §6). Violates Alloy's local-first,
  no-account design; Traycer needs it because teams share one epic. If multi-human ever
  matters, the webhook + event hooks (audit §13) are the local-first seam.
- **Cross-device sync / Hosts / clone-not-migrate** (research §10). Solves "my agents live on
  a server" — Alloy's answer for remote compute is Josh's existing SSH peer link, which needs
  no protocol, signing infrastructure, or per-method RPC versioning. Large cost, wrong axis.
- **Native inference subscription + credit/slot economy, rate-limit pause with $0.50 refills**
  (research §7–8). Alloy deliberately has no metered middleman. Its backoff/probation/starved
  taxonomy (audit §15) handles provider wobble MORE honestly than pausing automation until
  credits recharge.
- **Electron shell + GUI/renderer/CLI/shared-client package split** (research §1). Traycer is a
  team product with a cloud backend; Alloy is one pywebview window over one Python process.
  Adopting the shape would mean adopting their constraints for no gained feature.
- **Chat-vs-Terminal interface split** (research §2). In Alloy every seat is already steerable
  turn-by-turn AND resumable via stored CLI ids; fixed-launch one-shot sessions already exist
  as helpers. The distinction would duplicate concepts we have under better names.
- **Auto-generated mermaid diagrams of plans** (research, llms.txt mermaid page). Already
  tracked in `docs/competitor-feature-gaps.md` per audit §16 — cosmetic next to items above;
  fold into any future rendering pass rather than treating as a Traycer-specific lesson.
- **Cursor as a provider**. Their fifth integration; our registry makes adding providers one
  entry, and Cursor has no headless CLI account story comparable to the four we support.
  Revisit only if a CLI appears.
